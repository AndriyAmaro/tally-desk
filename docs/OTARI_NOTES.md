# Otari integration notes

The long technical notes of the `otari` branch, moved out of the README so that the README can stay short. The proofs, the scoreboard and the host table are in the [README](../README.md); the friction met on the way is in [FEEDBACK_LOG.md](FEEDBACK_LOG.md) and the first map of the gateway in [OTARI_MAP.md](OTARI_MAP.md).

## Run it through Otari (the `otari` branch)

With `OTARI_API_KEY` in the environment, every LLM call goes through the [Otari](https://otari.ai) gateway at `https://otari.ai/api/v1` and each role uses its own open-weight model from [`config/otari.json`](../config/otari.json). Without the variable nothing changes: the client above runs as before.

| Role | Catalog id | Vendor | What it does |
|---|---|---|---|
| `bull` | `openai/gpt-oss-120b` | OpenAI | the case for a long entry |
| `bear` | `nvidia/nemotron-3-super-120b-a12b` | NVIDIA | the case against it |
| `judge` | `deepseek/deepseek-v4-flash-0731` | DeepSeek | rules on the claims that passed the citation check |
| `checker` | `google/gemma-3-27b-it` | Google | re-reads each validated claim against the evidence it cites (advisory: it never changes the verdict) |
| `narrator` | `alibaba/qwen3-235b-a22b-instruct-2507` | Alibaba | extracts tokens and stance from the news headlines |
| `searcher`, `fetcher`, `sandbox`, `mcp` | `deepseek/deepseek-v4-flash-0731` | DeepSeek | drive one Otari tool each (web search, web fetch, code sandbox, MCP); they share the judge's model on purpose and bill to their own end users |

`python3 tools/otari_catalog_check.py` confirms against the public catalog (no key, no cost) that each id exists and is flagged `open_weights`.

- **Auth.** The key travels in the `Otari-Key` header. `Authorization: Bearer` and `x-api-key` also answered HTTP 200 on 2026-11-01; change `auth_header` in the config to switch. `OTARI_BASE_URL` overrides the base URL.
- **Receipt per call.** Each answer leaves an `otari-receipt/1` next to the block it produced (`llm.bull.receipt`, `llm.bear`, `llm.checker`, `llm.judge`, and `evidence.narrative.receipts` for the extraction batches): `request_id`, `provider`, `sent_model`, `served_model`, `served_by`, `attempt_count`, `fallback`, `duration_ms`, token counts, `cost_usd` (as Otari sent it) and `pricing_source`. A refused call leaves a receipt with the error code, the budget scope and `Retry-After`. The receipts are part of the sealed dossier, so the hash chain covers them. `replay` never calls a model: it re-derives the verdict from the frozen evidence and the frozen judge ruling, and it passes with the network cut.
- **Per-user budgets.** The role name is the `user` field once a service key exists (`send_user` in the config, or `OTARI_SEND_USER=1`). With an ordinary key Otari refuses that field, so it is off by default ([`docs/FEEDBACK_LOG.md`](FEEDBACK_LOG.md), entry 2).
- **Otari tools in a cycle (F3, hardened in F3.1 and F3.1b).** One decision cycle uses three more Otari features, each with a receipt and each frozen in the dossier so the replay never calls them again. (1) **Web:** one `otari_web_search` (about USD 0.01 a call) whose query names the coin the most voices converged on, asks for rallies and selloffs alike (so the narrative does not choose the story) and carries the date. Only article pages are kept (a path of its own, no tag or category index), at most three, one per domain, dated ones first; a source whose date is known (Otari's published date, or a `/YYYY/MM/DD/` in its URL) and older than three days is dropped, and one with no date is kept and marked `undated`. The first is read with one `otari_web_fetch`, and its opening text is sealed as an excerpt with a sha256, labelled as the model's verbatim relay of what Otari's fetch tool returned. The excerpt is then checked against our own GET of the page: runs of six consecutive words that are not just the title must be found in the page, in at least 80 percent of the runs, and the check seals the runs counted and found, the fraction, and the sha256 and size of the page we got (`excerpt_check`; `excerpt_verified` is true, false, or null when the page cannot be read without a browser or the excerpt is too short). That proves the text is on that page; it does not prove that Otari's tool is what read it. Items and excerpt have ids in the evidence index, so the analysts can cite them, and each dossier counts titles and excerpts apart (`llm.otari.evidence_use`). (2) **MCP:** spot prices read through Otari's managed MCP loop from the public keyless CoinGecko server (free), taken from the server's own `mcp_tool_result` block. The code the model sent must be the one price query asked for (a harmless `console.log` of the result aside) with no digit in it, else the prices are marked untrusted and unused. The trusted price is a second price source: it is compared with the newest candle's close, with a tolerance of 1 percent plus one hourly ATR for every hour of that candle's age. Beyond it the sources diverge, which is a blocking freshness class of its own (`classes.divergence`) beside the untouched age class (`classes.market`); the freshness `ok` turns false and the verdict refuses to decide (`BLOCKED_STALE`, no position) through the path the Python judge, the browser verifier and the CRE workflow all read, and a staleness reason already there is never overwritten. A missing or untrusted price blocks nothing; a trusted one that disagrees can make the agent refuse to trade, never trade. (3) **Code sandbox:** the verdict arithmetic as a self-contained script (it knows the stale refusal), with the frozen inputs and a new random nonce in its first line; it prints its result and `proof`, the sha256 of that whole line. The nonce stops a model from handing us an invented output at sealing time (it cannot compute the hash without running the code); the evidence for a third party is the sandbox's own result blocks and Otari's request id. The script runs in Otari's hosted sandbox through the Messages API declared as `code_execution_20250825` with `Otari-Code-Execution: otari`, which returns those blocks (the code it ran and its stdout). The dossier seals every run, the first whose code is exactly the code sent counts, and the replay recomputes offline, from the frozen dossier, the trust verdict on the MCP code, the prices, the check and, for the sandbox, that its stdout equals the local one, the proof lines match and the code run hashes to the code of this dossier; no sealed flag is believed. A block with an `error` is "not sealed", never a diverging verdict. Switches: `features` in the config, `OTARI_WEB_SEARCH`, `OTARI_MCP`, `OTARI_CODE_EXECUTION`. Measured prices are in [`docs/evidence/otari-drills.jsonl`](evidence/otari-drills.jsonl) (record `tool-costs`); `otari-drill mcp` is the cheap standalone proof. **Dossiers 794 and 795** were sealed by earlier versions and still replay with those versions' rules: 794 has generic landing pages none of which was cited, a version 1 sandbox block (no stale case, no proof line, model text as the only evidence) and a cycle snapshot (USD 0.014435) that leaves out the sandbox call, so it understates the cycle, whose receipts sum to USD 0.024612; 795 has the first MCP check (a flat 1 percent against the close) and a page excerpt checked with the weaker two-runs rule. For 795 the sealed spend (USD 0.034382) equals the sum of its receipts, none of its four web or MCP evidence items was cited by an analyst, and two narrative batches gave up after five tries on the 409 of entry 7. The guardrail is still attached and not evaluated; why is in [`docs/FEEDBACK_LOG.md`](FEEDBACK_LOG.md), entry 13.
- **What every receipt carries.** `role`, `end_user`, `sent_model` and `policy` (the routing policy named, else null), `request_id` with `request_id_source` (`otari` for the gateway's `Otari-Request-ID`; `client` with the id `client:<our Idempotency-Key>` when no gateway answer exists, as after a timeout or when the cycle cap refused the call, so no receipt is anonymous), `attempt_count`, `fallback`, `client_attempts` on failures and retried calls, and for guardrails the raw header, the parsed list and `guardrail_result` (`not_evaluated`, `pass` or `flagged`). Dossier 793, the first sealed with the service key, predates `policy`, `request_id_source` and `guardrail_result`; its receipts carry the same facts in the older fields. Retries happen only on the same `Idempotency-Key`, with growing waits (exponential, capped at 60 s) and at most five tries; the fallback is Otari's policy, never a loop of ours. From F3.2 it also carries `finish_reason`, `truncated` (the answer was cut off by the token limit), `prompt_sha256` (of the system and user text sent; the text itself is not stored) and `answer_sha256`, and the judge's receipt carries `route_rule`. The checker's answer is not used when it was truncated (`llm.checker.ignored`).
- **Judge routing (F3.2).** The judge is chosen by a deterministic rule sealed with its ruling (`llm.judge.route_rule`, copied into its receipt). A case is hard when the deterministic bull and bear scores, before the judge's vote, are less than 1.0 apart (1.0 is the most the vote can add: low 0.5, medium 0.75, high 1.0, so inside that zone the vote is the tie-breaker and a judge's mistake can change the action), or when 8 claims passed the citation check (both analysts at their cap of four). A hard case goes to the larger `deepseek/deepseek-v4-pro`, sent by its catalog id with Otari's automatic fallback across providers; every other case goes to the `vd-judge` policy, as before. No dashboard policy was created for this, and the hard route does not pass through the guardrail attached to `vd-judge`. Over the 369 recorded rulings of the earlier eras the rule would have sent 54 percent to the larger model (21 percent by margin, 41 percent by claim count, some by both), a share measured on rulings by other models, so the dossiers of the Otari era will show the real one; both numbers are in the config and sealed in each record. The replay recomputes the route from the frozen claims and arguments, with the thresholds sealed beside it, and calls no model. **Dossier 796**, the first with the rule: 8 validated claims, so the larger model ruled (margin 1.05, the claim-count branch); the bull analyst cited 2 of the 3 web source titles (both undated, so the dossier says so), none of the page excerpt and none of the MCP price, and the sealed spend (USD 0.036435) equals its receipts.
- **News for the analysts (F3.2).** When web items are in the evidence, the analyst prompt adds a note that they are untrusted third-party text, that a dated item from today counts for more than an undated or old one, and that an item must be cited only when it really bears on the claim ("never cite an item only to have cited it"); with no web items the prompt is exactly what it was. The fetched page is the most recent dated item, its excerpt line carries the item's date or `undated`, and the replay rechecks the sealed excerpt offline (hash, runs counted from the excerpt and the title, the verdict of the check from the sealed counts). Test runs have `tests/chain_guard.py` clear every `OTARI_*` variable and both chain keys, so a key exported in the shell can neither spend nor change a test.
- **No `route` block.** Otari sends counts (`attempt_count`, `fallback`), not the list of attempts, so in Otari mode no `route` or `routing_policy` is sealed; the receipt is the record. **Dossier 792, the first one recorded through Otari, still carries the legacy `route` field** (a one-item list rebuilt from its receipt, `policy: null`) because it was sealed before this was changed, on each of its bull, bear, checker and judge blocks, and the ledger is append-only. Read it as derived from the receipt, not as routing data from Otari. Later dossiers do not have it.
- **Base URL and pacing.** `OTARI_BASE_URL` must be `https://` (anything else is refused before a request, so the key never travels in clear text) and loses a trailing slash. Otari calls are not spaced by the 1.1 s Mistral interval: a burst of 12 parallel calls on 2026-11-01 got twelve 200s and no 429. `OTARI_MIN_INTERVAL` (or `min_interval` in the config) adds spacing if a limit ever shows up.
- **Fallback policies, drills and budgets (F2).** `sent_model` is the catalog id unless a routing policy is set for the role: `use_policies` and `policies` in the config (or `OTARI_USE_POLICIES=1`), or `OTARI_POLICY_<ROLE>` for one role. The receipt then shows the policy as `sent_model`, the model that answered as `served_model`, and `fallback` and `attempt_count`. `OTARI_USER_<ROLE>`, `OTARI_END_USER_BUDGET_<ROLE>` (header `Otari-End-User-Budget`) and `OTARI_MAX_TOKENS_<ROLE>` let one role run as a drill user on a tiny budget. A refused call (403 `budget_exceeded` with `Otari-Budget-Scope` and `Retry-After`, 402 `insufficient_funds`) leaves a refusal receipt in the dossier, the command line prints `[otari judge] NOT answered: ...`, and the decision is still recorded.
- **Service key, drills and the guardrail.** The key is a service key: each role is billed to its own end user (`vd-bull`, `vd-bear`, `vd-judge`, `vd-checker`, `vd-narrator`, `vd-searcher`, `vd-fetcher`, `vd-sandbox`, `vd-mcp`) on the dashboard budget `vd-analyst`, sent as `Otari-End-User-Budget` (the budget id, not its name). That each end user really sits on that budget is not assumed: `otari-drill users` reads `GET /end-users` for every role and the evidence file holds the `budget_id` of each (an end user takes its budget only when it is created, so one born without the header is replaced by a new name, never patched). The judge sends the routing policy `vd-judge`, which has a mandatory `prompt-injection` guardrail attached in monitor mode. **The guardrail is attached, not evaluated:** the hosted Otari reports `valid: null` and `score: null` on every call, including a hostile prompt, so it is listed here as attached and not counted as a feature exercised until a call returns a non-null `valid`; the receipt keeps the header raw and parsed and `guardrail_result: not_evaluated`, never a pass. `python3 -m verdict_desk otari-drill fallback|budget|users|all` runs two real drills and appends their receipts and usage rows to [`docs/evidence/otari-drills.jsonl`](evidence/otari-drills.jsonl) (not to the ledger): `fallback` (billed to its own end user `vd-drill-fallback`, not to the production `vd-judge`) sends a prompt too long for the 32k-context main model of the policy `vd-judge-drill`, so Otari serves the backup (`Otari-Fallback: true`, `Otari-Attempt-Count: 2`, two usage rows); `budget` bills the end user `vd-drill` on the USD 0.01 budget `vd-drill-tiny` and keeps the 403 `budget_exceeded` refusal as a receipt.
- **Cycle caps.** Behind Otari's own budgets the app keeps a second line with two caps, so a tool that costs a cent a call can never use up the money the analysts and the judge need: `cycle_cap_usd` (default 0.02, `OTARI_CYCLE_CAP_USD`) for bull, bear, judge, checker and narrator, and `tool_cap_usd` (0.06, `OTARI_TOOL_CAP_USD`) for the four tool roles. Each is the spend after which no new call of that group starts in a decision cycle, counted from `usage.cost_usd`. Neither is a reservation: calls already started (the narrative batches run in parallel) can finish, so the spend can pass a cap by what those calls cost. Once reached, each further call is refused before it is sent and leaves a client-side refusal receipt (`cycle_cap_exceeded`, scope `cycle` or `cycle_tools`, `source: client`, id `client:<the call's Idempotency-Key>`). The spend is sealed in `llm.otari.cycle` after the sandbox call (`total_spent_usd` is the sum of the receipts).
- **Cycles that were run and discarded, and proofs that were upgraded.** Two live cycles were thrown away before anything was committed, stamped or pushed, and their dossiers are not in the ledger: the first test cycle of the Otari era (four of nine narrative batches lost to the 409 of entry 7, dossier 792 was recorded again after the fix) and the first cycle of the hardened tools (a sandbox call cut short by `max_tokens`, a model that typed a plausible answer with an invented proof, a too-strict MCP code check; it cost USD 0.0563 and is described in [`docs/FEEDBACK_LOG.md`](FEEDBACK_LOG.md), process notes). The OpenTimestamps proofs of the heads 785, 788, 791, 792 and 793 were rewritten by `ots upgrade` in commit `1fbf0d1` (the commit message lists 785 to 792 and leaves 793 out by mistake): 785, 788, 791 and 792 now carry Bitcoin attestations (block heights 974125 to 974139, plus two later ones the upgrade added); 793 carries one too (block 974160, read with `ots info`), next to its pending calendar entries. The proofs of 794 and 795, the newest, are still pending and have not been upgraded.
- **Retries.** A gateway timeout (HTTP 504) is retried with the same `Idempotency-Key`, so a lost reply is not billed twice. Budget and credit refusals (402, 403) are never retried.

```bash
export OTARI_API_KEY=...      # from the Otari dashboard; never commit it
VERDICT_DESK_APPEND_PUBLIC=1 python3 -m verdict_desk decide-v6 BTCUSDT --config config/voices.json
python3 -m verdict_desk verify && python3 -m verdict_desk replay
```
